# 2026-11-09

## 修复 desktop 扫码登录确认后无反应
- 根因：desktop/mobile 等确认结果纯靠 WS 推送（`scan_login_session_update`，`packages/services/src/scan-login.ts` 的 subscribeScanLoginSession），无轮询兜底；harmony 端本来就 1.5s 轮询所以正常。wss 被代理/防火墙拦截或旧版 WS 地址（`https://www.audiodock.cn` 无 `/ws`，能连上但收不到事件，2026-04-03 提交 94618ae8 改过）都会静默无反应。
- 修复：subscribeScanLoginSession 增加轮询降级——3s 宽限期内 WS 无任何推送则启动 1.5s 轮询 getScanLoginSession；按 status 去重防 WS/轮询双通道重复通知；终态（consumed/success/failed/expired）停止轮询；unsubscribe 清理所有定时器。改完需 `cd packages/services && pnpm build`（已执行，dist 已验证）。
- 服务端线索：云端 audiodock.cn 推送链路实测正常；仓库内 services/api 的扫码登录是旧自部署版（缺 /report 路由、无 WS 推送网关），线上跑的不是这份代码。

## 修复 mobile 扫码 desktop 无反应（第二轮）
- 现象：desktop 轮询修复后 hm 扫 desktop 正常，mobile 扫 desktop 仍完全无反应（claim 都没发生）。
- 根因判断：mobile 扫码方（apps/mobile/app/scan.tsx）与 hm（ScanPage.ets）逻辑等价，差异在识别能力——hm 用系统 ScanKit，mobile 用 expo-camera 默认配置；desktop 二维码是 antd QRCode size=180、默认纠错 M，内容 ~150 字符 JSON，码点过密，普通相机解码器扫不出（表现为"扫了没任何反应"）。
- 修复：① desktop Login/index.tsx 二维码 size 180→240、errorLevel="L" 降低密度；② mobile scan.tsx CameraView 加 barcodeScannerSettings={{barcodeTypes:["qr"]}} 提升识别率；③ handleBarcodeScanned 入口加 console.log + trackEvent("scan_login_qr_detected") 便于定位断点。
- 排查手段：mobile 扫码后看日志有无 "qr detected"——没有=识别层问题，有但没跳转=claim 失败（会有 Alert）。

## 修复 mobile 扫码 desktop 无反应（第三轮，真根因）
- 用户日志显示 qr detected 正常、跳转 scan-confirm 正常，但会话停留 waiting_scan（hasNativeAuth/hasPlusAuth 全 false）→ claim 实际未生效。
- 线上实测定位双 bug：① 云端 claim 接口用 class-validator 强校验 sourceBundles，**internal 和 external 都必须非空**，用户云端数据源配置 internal:"" → 整个 claim 被 400 拒绝；② 服务端错误以 **HTTP 200 + {code:400} envelope** 返回，`scanLoginRequest` 拦截器原样放行 → axios 不抛错 → scan.tsx 误判成功跳确认页 → 静默失败。hm 正常因为 claim 恒发 sourceBundles: []。
- 修复：① packages/services/src/scan-login.ts 拦截器加 envelope code 检查（非 200/201 抛 Error(message)），所有端生效；② mobile collectMobileScanLoginPayload 和 mini collectMiniScanLoginPayload 加 sanitizeConfigs：internal/external 互补回填、双空丢弃。
- 已 pnpm build 重建 @soundx/services。
- 服务端惯例：plus 服务（audiodock.cn）错误恒 HTTP 200 + code envelope（401 也是，见 isPlusUnauthorizedPayload），新写 plus 请求必须查 code。

## 第四轮：mobile 闪退 + hm 扫码无效排查
- 线上实测新发现：① confirm 必须传 selections（空数组可，缺省 400 "selections must be an array"）；② **/report 接口在线上 404**（云端没部署该路由，与仓库旧版 controller 一致），各端 reportScanLoginResult 的 .catch 兜底，成功回执实际走 socket 广播；③ 用 dist 产物 node 全链路模拟（create→subscribe→claim→confirm→consume→report）通过，状态序列 waiting_confirm→confirmed→consumed 正常，services 层无崩溃点。
- **二维码 TTL 5 分钟且三端都不自动刷新**（desktop Login、mobile login-form、member-login 只在 mount/横屏切换时创建会话）——QR 过期后扫码方 claim 收到 400/500 envelope → hm 报"扫码失败"。这是"hm 扫码无效"的最可能原因（测试间隔超 5 分钟）。
- 修复：三端 QR 展示侧加 expiresAt-10s 自动 createTargetSession 定时器（min 5s 防时钟偏差死循环）；scan-confirm 渲染 sourceBundles 加 `|| []` 防御（report 广播的 partial status 只有 status/sessionId 两字段）。
- mobile 闪退结论：代码层全部有守卫、metro bundle 编译通过（200）、dist 模拟无异常 → 最可能是 services dist 重建后 metro 缓存不一致导致的启动崩溃，让用户 `npx expo start --clear` 重启 metro 再验证，复发需 redbox/logcat 定位。

## mobile 播放详情页 Android 无关闭动画修复（自驱动转场，仅 Android）
- 症状：iOS 进出场正常；Android 关闭播放详情页时页面直接消失、无滑出动画。
- 根因：react-native-screens 4.16.0（Fabric）Android 端 pop 时 React 立即卸载屏幕视图，原生退场动画（rns_slide_out_to_bottom）来不及播放——mounting override delegate 机制在该版本有已知缺陷（4.17.0 才修 #3241）。fullScreenModal 在 Android 端本就不走独立窗口（普通 Fragment），原生 pop 动画链路不可靠。11-08 的 b7401868 曾做过全端自驱动转场但当天被 revert（原因未记录），后续 layerBelow 方案仍用原生转场。
- 方案（iOS 零改动，仅 Android 分叉）：
  - `_layout.tsx` player 路由：Android → `transparentModal` + `animation:"none"` + `gestureEnabled:false` + contentStyle 透明；iOS 保持 `fullScreenModal` + `slide_from_bottom`。
  - `player.tsx`：`isSelfDrivenTransition = Platform.OS==="android"`；`transitionTranslateY`（Android 非 embedded 初始=height）进入 260ms 滑上；`closePlayer` Android 先 220ms 滑到屏幕底部再 router.back()（closing ref 防重复触发，进场中先 stopAnimation）；`renderWithTransition` 包裹全部 4 个 return（iOS/embedded 直接透传）。
- 配套机制衔接：transparentModal 是 translucent，下层 (tabs) 保持挂载不 detach → JS 滑动时下层页面 + layerBelow 底部栏（zIndex -1 + padding 条带透明，11-08 机制）原地透出，效果 =「播放页从底部栏上方滑过」。
- 注意：此前 revert 的自驱动方案是两端一刀切（iOS 也被迫 JS 驱动且丢了下滑手势），本次仅 Android 分叉规避了该问题。
- 验证：tsc 改动文件 0 错误。待真机验证：Android 打开/关闭播放页滑动动画、底部栏透出、硬件返回键、横屏关闭、通知/widget replace 进入路径。
