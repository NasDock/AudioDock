# 2026-09-19

## mobile 新歌播放需二次点击 + 切下一首暂停修复

**现象**：改动后新歌需要点两次播放按钮才出声；播放完当前歌曲自动切到下一首时停在暂停状态。旧歌（缓存命中）正常。

**根因**（logcat 真机验证）：
```
00:30:57  Playing track: 256, URI: https://...track/stream/256?quality=lossless
00:30:57  [Player] Pre-loading ±5 around index 6    ← 预下载 10 首启动
00:31:09  An error occurred: android-io-bad-http-status  ← 12s 后播放流失败
```
10 首预下载与当前播放流同时并发请求服务器，带宽/连接数竞争导致播放流异常。旧歌走 `file://` 本地路径零网络请求，所以正常。

**修复**（`PlayerContext.tsx` 三处）：
- `PlaybackActiveTrackChanged` 预下载：从「10 首同时 forEach 并发」改为「最多 2 首并发（Promise.all 分批）+ 延迟 3s 等当前曲目先缓冲」。
- `playTrackList` 后台升级（当前+下一首）：同样延迟 3s，2 首并发。
- `playTrack` 单曲后台下载：延迟 3s 触发。

**原则**：当前曲目的流请求永远优先拿到带宽，预下载只在它完成初始缓冲后开始，且最多 2 并发。

## hm / desktop 预下载并发限制同步

- **hm**（`PlayerStore.ets`）：`triggerPreloadAround` 和 `triggerCacheWhilePlaying` 都加 3s 延迟；预下载从「for 循环逐个触发但不等待」改为「最多 2 首并发（Promise.all 分批）」。`hvigorw assembleHap` 通过。
- **desktop**（`Player/index.tsx`）：预下载 effect 加 3s `setTimeout` 延迟；web 模式复播缓存下载（`getCachedAudioUrl` 未命中时的 `cacheAudioInBackground`）同样延迟 3s。
