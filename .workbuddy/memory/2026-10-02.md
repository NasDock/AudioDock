# 2026-10-02

## 曲库扫描（全量/增量更新）P0 提速

背景：NAS 性能低、数据多，用户反馈 `POST /import/task`（mode=incremental/full）很慢。根因：两种模式每次都全量重解析每个文件（parseFile + 指纹 + 每首歌刷父级状态 ~15-20 条 SQL），无「未变化跳过」。

P0 改动（已实施，tsc 通过）：

- **mtime 短路**：`ImportService.buildLocalTrackIndex()` 预载 `source=FILE 且 status=ACTIVE` 的 `path→{id, mtimeMs}`（只索引 ACTIVE，TRASHED 不跳过以维持「文件仍在则复活」语义）；`makeShouldSkip(basePath, type)` 按 `convertToHttpUrl`（music→`/music/`，audiobook→`/audio/`）+ 转码 URL（`getAudioTranscodedFilePath/PublicUrl` 确定性可算）反推候选 key，mtime 容差 2s（防 MySQL DATETIME 秒级截断）命中则计入 processedTrackIds 并推进进度计数。**STRM 不跳过**（track.path 是远端 URL 无法反推）。MV 扫描（scanMv/mv 表）未接入。
- **utils 扫描器钩子**：`LocalMusicScanner` 新增 `ScanOptions.shouldSkip(filePath, stat)`，`traverse` 在 parseFile 前检查；scanMusic/scanAudiobook 透传第三参（可选，向后兼容）。**改完必须 `cd packages/utils && pnpm build`**（father 构建，入口指 dist）。
- **父级状态延后去重**：`processTrackData` 末尾两次 `updateParentStatus` 改为 `markAlbumDirty`（dirtyAlbumIds Set）；flush 点：startImport 扫描结束后（cleanupOrphans 前）、catch 兜底、runSingleWebDavTarget 末尾、watcher handleFileAdd 的 processTrackData 之后。
- ImportTask 新增 `skipped` 字段（跳过数，供任务中心展示）。

遗留（P1/P2 未做）：cleanupOrphans 仍逐专辑循环 updateParentStatus（N+1，全量模式残余成本）；无并发池；countFiles 与扫描两遍目录树且 readdirSync 阻塞事件循环；WebDAV 源未做 mtime 短路（其 track.path=远端 URL 可直接索引，扩展容易）。

注意：根目录 `api.json` 是早期 NestJS OpenAPI 骨架，已过期，不含 import/task 等现行接口。
