## desktop 版本更新「去下载」点了没反应 —— 已修
根因两条，都在 desktop 端：

1. **打开链接用了未注册的插件**：`UpdateModal` / `MarkdownContent` / `platform.ts` 都 `import { open } from '@tauri-apps/plugin-shell'`，但 `src-tauri/Cargo.toml` 只有 `tauri-plugin-opener`，capabilities 里也只有 `opener:allow-open-url`，没有 shell 权限 → `open()` 必然 reject，又被 `.catch(console.error)` 吞掉 → 点击完全无声。
   修法：`utils/platform.ts` 的 `tauriOpenExternal` 改走已有 Rust 命令 `invoke('open_url', { url })`（`commands::open_url` → `app.opener().open_url`），失败才 fallback `window.open`；`MarkdownContent` 复用 `tauriOpenExternal`。**别再引 plugin-shell**。
2. **下载地址来源不稳**：desktop 原来从 GitHub API `/releases/latest` 的 assets 里按 UA 后缀匹配 dmg/exe，未认证 API 有速率限制且国内不稳。
   修法：新增 `apps/desktop/src/services/update.ts`，与 `apps/mobile/src/services/update.ts` 同构，走自有后端 `GET {PLUS_API_BASE_URL}/download/latest?product=audiodock`（`plusRequest`），拿 `{ version, files[] }`；`files[].platform` 实测取值 = `macos-arm64 / macos-x64 / windows-x64 / windows-arm64 / linux-appimage / linux-deb / android`（6 个桌面项当前都齐，实测直链 GET Range 206 可下）。
   - `resolveDesktopPlatformKey()`：Tauri 用 `plugin-os` 的 `platform()/arch()` 精确判定；浏览器用 UA + UA-CH `getHighEntropyValues(['architecture'])`，拿不到时 Windows 默认 x64、macOS 默认 arm64。
   - `pickDesktopDownloadFile()`：精确 → 同系统另一架构 → `linux-appimage` 兜底。
   - changelog 仍从 GitHub Release body 拉（`classifyRelease` 平台过滤不动），拉不到 fallback `update.defaultReleaseNotes`。
3. **预签名 URL 只 5 分钟有效**（`X-Amz-Expires=300`）→ 新增 `startDownload()`：点按钮时重新拉一次 `/download/latest` 换新直链再打开，避免弹窗停留久了点开 403。弹窗里顺带展示安装包文件名 + 体积。
4. `UpdateModal` 新增 `onDownload` prop（由 `App.tsx` 传 `startDownload`）；web 端行为不变（仍只提示 + 关闭，不渲染下载按钮）。

验证：`tsc -b` + `vite build` 通过；用 tsx 直跑 service 层对真实接口，6 个平台均精确命中；`getLatestVersion` 在 node 下正常解析。

注：`apps/desktop` 的 `eslint.config.js` 引用 `typescript-eslint` 但 devDependencies 没装，lint 跑不起来（既有问题，与本次改动无关）。

## 扫码登录：第三方源凭据同步 + 单源过滤（commit 35313f00）
- 问题1「其他数据源也要能扫码登录」：Subsonic/Emby/飞牛无 nativeAuth token，payload 原本只带 sourceConfig 地址（id/internal/external/name）→ 目标端拿到地址也登不上。
- 方案：`ScanLoginSourceConfig` 加可选 `username/password`（packages/services + services/api 服务端类型；服务端 claim/consume 对 payload 透传，无需改逻辑）。collect 端按 `creds_${type}_${addr}`（内/外网各试一次）补凭据；apply 端落盘 creds_ 并**剥离后再合并 sourceConfig**（凭据不进 sourceConfig 存储）。
- 问题2「单源过滤」：`collectMobileScanLoginPayload(onlyType?)`；`/scan?sourceType=X` 从 login-form 进入只同步当前源（nativeAuth 不属于该源时置 null，避免目标端被切到无关 AudioDock）；personal 入口不传 → 全量，scan-confirm 页本就有勾选。
- 凭据存储约定：`creds_${type}_${address}` = {username, password}，mobile AsyncStorage / desktop localStorage 同构（登录页 handleSubmit、LoginModal 都按此写）。
- desktop collect/apply 同步改（apps/desktop/src/utils/scanLogin.ts）。
- 未动：hm ScanPage 只发 nativeAuth+plusAuth（sourceBundles 空）；member-login 的 /scan 入口仍全量。
