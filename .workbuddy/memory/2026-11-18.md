# 2026-11-18

## 修复：/auth/check 恢复为登录前可达的连通性探针（auth.controller.ts + guard 回滚 + desktop 登录页）
- 起因：用户反馈加了 access token 后 `/api/auth/check` 未登录访问 401。考古结论：
  - 服务端 `/auth/check` 自 b065114d（2026-01-06）诞生起就非 @Public，JWT 一直覆盖它——但**设计意图是登录前连通性探针**：desktop 登录页最初 `tryAddress` 是「有响应即算可达」（d037b5ff）。
  - 语义被破坏是在 23cae185（接入飞牛 #204）：改成 `code !== 200 判负`，未登录探测必失败。与 access token 提交时间相邻导致归因混淆。
  - 第一版修复（guard 里给 /auth/check 开 access token 白名单）方向不对，已回滚。
- 最终方案（双语义智能探针）：
  - `auth.controller.ts` `/auth/check` 加 `@Public()`：无凭证→200；带 Authorization/X-Access-Token 则手动校验（AuthService.verifyToken / AccessTokenService.resolve），失效→body 401。
  - 保留 401 的原因：desktop Header、mobile (tabs)/_layout 仅靠 `check()` 的 401 做登录过期自动登出（desktop axios 拦截器的 HTTP 401 分支因 filter 包 200 而是死代码）。
  - desktop `Login/index.tsx` tryAddress：`code===401` 也算可达（防「token 过期→check 401→判连接失败→永远无法重新登录」死锁）。
- 验证：nest build + desktop tsc 过；3001 临时实例 9 场景 curl 全过（无凭证 200 / 有效 JWT 200 / 伪造 JWT 401 / 有效令牌 200 / 无效令牌 401 / 令牌访问 /auth/me 仍 403 / 无凭证 /auth/me 仍 guard 401）。测试实例与测试 token 已清理。
- 环境坑：nest API 的 .env 按 **process.cwd()** 加载（jwt.config 读 JWT_SECRET），从仓库根 `node dist/main` 会拿不到 secret → 所有 JWT 401；必须 CWD=services/api 或内联传环境变量。dev.db 实际在 `packages/db/prisma/`（Prisma 按 schema 位置解析相对路径，与 CWD 无关）。
