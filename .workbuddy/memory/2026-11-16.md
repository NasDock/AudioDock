## mini → 全屏「背景色闪一下 / 重新下大封面」修复（mobile + hm）

- 根因（两端同构）：取色**只在全屏页挂载时**触发（`useCoverVisual` 唯一调用点 player.tsx / hm `refreshCoverColor` 仅在 PlayerPage），mini 态 `dominantColor` 内存 Map 是空的 → 首帧 coverColor=null 退中性黑，异步「下载 96px PNG → 解码取色」回来才跳成主题色；且 mini 用 96 档、全屏用 900/600 档 + 背景 300 档，URL 不同导致图片缓存不命中，进全屏重新下载大图。
- 方案：曲目一确定就在全局层闲时预热（mobile `PlayerProvider` / hm `PlayerStore.notify`），**两档时机**——主题色立即起步（决定闪不闪，不能等闲时），大封面延迟 3s（对齐项目既有 `triggerCacheWhilePlaying` / `setTimeout(3000)` 的「让音频先缓冲」范式）。放全局层而非 MiniPlayer 组件：覆盖冷启动恢复、车机 embedded、播放流转等全部入口。
- **mobile**（3 文件）
  - 新增 `src/utils/playerVisualPrefetch.ts`：`fetchCoverVisual()` 填主题色 + 本地磨砂图（data URI）缓存，`useCoverVisual` 首帧同步读；闲时 `Image.prefetch` 900/300 档。带 mediaHeaders 或外链封面跳过 prefetch（不支持 headers；外链 `getImageUrl` 直返原 URL、与尺寸无关，mini 已加载过）。
  - `src/context/PlayerContext.tsx` 挂 `useEffect([currentTrack?.cover])`（按 cover 而非 track 对象，飞牛歌词并回 currentTrack 不重复调度）。
  - `src/utils/dominantColor.ts` 加 `invalidateCoverVisual()`。
- **hm**（5 文件）
  - 新增 `utils/coverCache.ets`：通用封面落盘缓存。落盘路径复用 `fileCache.coverPath(url, 'jpg')`，与 `fnosCover.resolveFnosCover` **同一个文件**互相命中；飞牛源委托 `resolveFnosCover` 共用 inflight（避免两个任务并发 TRUNC 写同一文件）。导出同步索引 `getCachedCoverUri/coverDisplayUri`、`hydrateCachedCoverUri`（冷启动只查磁盘不下载）、`prefetchCoverToDisk`。
  - `components/CoverImage.ets` `buildUrl()` 优先本地 `file://`；`pages/PlayerPage.ets` 背景图走 `coverDisplayUri`；`context/PlayerStore.ets` 在 `notify()` 里按 cover 去重触发预热；`utils/dominantColor.ets` 加 `invalidateDominantColor()`。
  - 关键：`CoverImage` 只在**预热过的 URL** 上走 file://，列表缩略图（96/128 档）不受影响，无回归。
- **防御（重要）**：预热可能在冷启动早期源地址/鉴权未水合时失败，若把 `null` 写进缓存，全屏会一直读到「已解析但无色」，反而彻底丢失主题色（比闪一下更糟）。故两端预热失败即清缓存，播放页挂载时重新解析。
- ArkTS 坑：`arkts-limited-throw` —— catch 参数不能 `throw e`，必须 `throw new Error(String(e))`；`import type { Rgb }` 不能漏。
- 验证：`pnpm exec tsc --noEmit` 输出与改动前**逐行一致**（30 行全是仓库既有错误，无新增）；`hvigorw --mode module -p product=default -p module=entry@default assembleHap --no-daemon` → BUILD SUCCESSFUL in 9.5s（中途因 `throw e` 失败一次，已修）。**两端均未真机验证**：预热时序、file:// / Image.prefetch 的实际缓存命中需实机过一遍。

## 排查 desktop / mini 是否有同类问题（同日续）

- **desktop：确认不存在，未改代码**。`Player` 在 `App.tsx:337` 是 Routes 之外的常驻组件，`useCoverDominantColor(coverUri)` 在 `Player/index.tsx:154` 顶层 → 切歌即取色并写模块级 Map，等价于天然全局预热，与 Drawer `isFullPlayerVisible` 生命周期无关（`destroyOnClose=false`）。取色 + 全屏模糊背景 + 底部条封面都用 300 档同一 URL（240 经 `bucketWidth` 也量化到 300）；唯一不同档是全屏大封面 600/q80，但 `LazyImage` 有「new Image 后台预载 + 加载完成前保留旧图」，不影响背景色。Tauri `mini` 是独立 WebviewWindow（`#/mini` 独立 React 树），根本不画封面主题色背景，返回走 `show_main_window`。
  - 旁支风险（未改）：`useCoverDominantColor.ts:96` 在 `img.onerror` 时 `cache.set(src, null)` 永久缓存失败，同一 URL 不再重试；冷启动 baseURL 变化会换 src 所以通常自愈。
- **mini：只有「大封面重新下载」半个问题，已修**。mini 端**没有**取色/主题色渐变，全屏背景写死 `#fff`（mini 条也是 `#fff`）→ 不存在背景色跳变；但 mini 条 128 档 / player 页 600 档 URL 不同，微信 `<image>` 按 URL 缓存不命中，进全屏才下大图 → `.player-artwork` 先露 `#eee` 灰底。
